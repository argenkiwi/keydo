Fixed in src/keyboard_impl/dispatch.rs process_event: on key-down the cache entry now stores layer: 0 (sentinel) instead of the resolved lookup layer; on key-up the descriptor-execution layer is now entry.dl instead of entry.layer, matching keyd keyboard.c exactly (ce->layer=0 on cache_set, ce->layer only mutated by activate_layer; dl=ce->dl read on release). Verified: (1) full 73-test suite still green, (2) 5000-run randomized fuzzer against the real kenkyo config now shows 0 failures (previously 10/5000, including the debug_assert panic 'deactivate_layer called on inactive layer N' and permanently stuck output keys), (3) new permanent regression test test_io.rs::test_swap_does_not_hijack_unrelated_key_cache_entry — confirmed to panic on the pre-fix code and pass on the post-fix code. Root cause recap: swap()'s search for the key holding the source layer (actions.rs Op::Swap, `ce.layer == dl`) was matching every key resolved while that layer was active, not just its true holder, because every key-down mis-tagged its own cache entry with the lookup layer.
