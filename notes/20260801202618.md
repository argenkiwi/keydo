While verifying the new keydo proptest suite actually catches the historical chord-slot-aliasing bug (MAX_ACTIVE_CHORDS hardcoded to 8 instead of derived from the reserved keycode range), reintroducing the exact historical bug and re-running the proptest showed it passing cleanly, repeatedly, across multiple random seeds.

Root cause: that bug is a semantic correctness bug (a genuine playcd keypress silently resolves to the wrong action) — it does not violate any capacity/uniqueness/panic invariant, which is all the proptest checked (cache slot uniqueness, chord queue/timeout bounds, no panics). More fundamentally, the bug only exists if the crate is built with the wrong constant — a runtime property test explores behavior of a fixed, already-compiled binary, so it structurally cannot discover "what if this compile-time constant were wrong," no matter how many cases or how cleverly the generator is designed.

Fix: added a const-context assertion (const _: () = assert!(MAX_ACTIVE_CHORDS <= (KEYD_CHORD_MAX - KEYD_CHORD_1 + 1) as usize);) next to the constant in keyboard_types.rs. Verified by hardcoding MAX_ACTIVE_CHORDS = 8 again: cargo build now fails outright with an E0080 const-eval panic, before any test even runs — strictly stronger than the runtime-only defense.

General lesson: when a fix derives one constant from another (or otherwise encodes an invariant purely in compile-time values), add a const-assertion at the definition site as permanent defense-in-depth. Don't assume a fuzz/property-test suite covers this class just because it covers the runtime behavior the constant feeds into — verify by literally reintroducing the historical bug and watching the test suite fail (or, as here, discovering it does not).
