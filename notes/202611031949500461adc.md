The macOS and Windows Vkbd repeat threads used to thread::sleep for the delay and interval and only check the revision afterwards. A key pressed during a previous key's delay then waited a stale delay plus a full new one. They now use Condvar::wait_timeout_while on revision == rev, and send_key notifies on both arm and cancel. Ordering invariant: the repeat thread posts or injects while holding the shared lock, and send_key arms or cancels (bumps the revision) under that lock before posting the real key event. A release therefore always cancels before its key-up goes out, so no stale repeat key-down can follow it. This is deadlock-free only because the tap and hook callbacks ignore our own injected events and never take this lock. Separately, the daemon replaced the single global timeout_ms with KbdRuntime.deadline per keyboard. kbd_process_events returns that keyboard's own earliest timeout, so the deadline is overwritten rather than min-merged. kbd_rt must stay index-aligned with keyboards; every method that grows or replaces keyboards calls sync_kbd_rt. Do not cache the layer-indicator LED state: LED 1 is the CapsLock LED, which the vkbd LED-feedback path also writes, so a cache goes stale.
