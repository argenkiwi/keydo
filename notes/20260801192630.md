Fixed by deriving MAX_ACTIVE_CHORDS from the actual reserved sentinel range instead of hardcoding it: `pub const MAX_ACTIVE_CHORDS: usize = (KEYD_CHORD_MAX - KEYD_CHORD_1 + 1) as usize;` in keyboard_types.rs (= 3, down from the old hardcoded 8). This bounds active_chords to exactly the 3 reserved synthetic codes (197-199), so slot indices can never compute to real Linux KEY_* codes like KEY_PLAYCD (200) again.

Also added an explicit upper bound in resolve_descriptor (dispatch.rs): `code >= KEYD_CHORD_1 && code <= KEYD_CHORD_MAX` instead of just `code >= KEYD_CHORD_1`, as defense-in-depth so the invariant is visible at the call site rather than relying solely on active_chords.len() matching MAX_ACTIVE_CHORDS.

Rejected reserving more synthetic codes instead: checked KEYCODE_TABLE in keys.rs and the byte range 197-255 is fully packed with real key/button names (playcd, pausecd, scrollleft, scrollright, dashboard, suspend, mouse buttons, etc.) with zero free slots - confirmed via vkbd.rs that these codes pass verbatim to uinput as real KEY_* output, so widening the range would permanently break real hardware keys for some users.

Traced the no-free-slot fallback (relevant now that only 3 concurrent chords are allowed): when resolve_chord finds no free slot, chord_code stays 0 and the chord raw queue replays through kbd_process_events while state=Resolving, falling through to ordinary per-layer dispatch for each raw key - this is the exact same code path abort_chord already uses and was already tested, so no new fallback branch was needed.

Added regression test test_fourth_simultaneous_chord_does_not_alias_real_keycode in test_io.rs: holds 4 disjoint chords (exhausting the 3 slots), then presses real playcd, and asserts it resolves to its own binding rather than the failed 4th chord's action. Fails on the pre-fix code, passes after.
